# amigo in T3 Code: a `t3` terminal backend

Status: plan, not started. Written 2026-11-27 from a survey run inside a T3 Code thread (t3 v0.1.13).

This reverses the 2026-11-22 "herdr-app only" decision for one more host. herdr-app stays as it is.

## What the survey found

- `amigo` refuses in T3: `terminalBackend` needs `HC_TERMINAL_ID`. T3 threads carry `T3CODE_THREAD_ID` and `T3CODE_CLI_PATH` instead.
- amigo depends on launching `claude` itself: `--settings` (its Stop / UserPromptSubmit hooks), `--append-system-prompt-file` (the contract), `--name` / `--session-id`, `crossSessionInbound`. A T3 thread is started by T3 through the Agent SDK, so none of these flags can be passed.
- User-level hooks in `~/.claude/settings.json` DO run inside T3 Claude threads (verified: `guard-edits.js` blocked a probe write in this thread).
- `t3 thread` CLI has `start` (project, message from stdin, `--provider --model --option effort=`, `--worktree`, `--title`, `--wait --json`), `send` (queued as the next turn, never typed, never interrupts), `show --json` (status, activeRunId, pendingRequestCount, worktreePath) and `list --json`. `t3 project add|remove` registers folders.
- Missing from the CLI: interrupt, archive/close. They exist only as T3 MCP tools (`t3_thread_interrupt`, `t3_thread_update`), which the lead thread can call but amigo's Node CLI cannot.
- T3 threads have no labels, so the herdr "foreign terminal" check (task + home labels) needs a different ownership record.

## Design

| herdr-app today | t3 backend |
|---|---|
| amigo lead = claude started by `amigo` with hooks + contract | lead = the T3 thread you type `/amigo` in; `amigo` registers `T3CODE_THREAD_ID` as the lead (session lock keyed by thread id) and prints the contract + digest as the skill output; re-injected after compaction by the SessionStart hook |
| per-session `--settings` hooks | one user-level dispatcher hook (`amigo _hook-dispatch <event>`) installed by `amigo install-skill`; exits at once unless `T3CODE_THREAD_ID` is a registered amigo lead or crew thread |
| crew tab: `herdr-app do space.new/tab.new` running the agent CLI | crew thread: `t3 project add <leased worktree>` then `t3 thread start <worktree> - --provider --model --option effort=… --title "<id> <title>"`, brief on stdin |
| `send`: hc types a line once the agent settled | `t3 thread send <thread> -`: queued, no settle/dialog states (`input` is always `ready`; `dialog` when `pendingRequestCount > 0`) |
| `state`: hc liveness + agent status word | `t3 thread show --json`: running = busy, settled/idle = idle, missing = absent |
| ownership: tab labels | `~/.amigo/state/t3-threads.json` (task id, thread id, project id, home tag); a thread not in it is `foreign` |
| wake: watcher armed by the lead's Stop hook | the watcher wakes the lead with `t3 thread send <lead thread> "<wake>"`; the Stop hook keeps only the turn-end guard |
| crew → amigo: SendMessage to `amigo` | `amigo report` + watcher wake (SendMessage addressing of T3 threads is unverified) |
| `interrupt` / `close` | interrupt: amigo asks the lead to call `t3_thread_interrupt` (playbook step) until T3 ships a CLI verb; close: `t3 project remove` + archive via `t3_thread_update` from the lead |

Worktrees stay amigo's: treehouse leases them and amigo's isolation check runs as today. T3's own `--worktree` is not used, so the pool, the branch naming and the landed-work test do not change.

## Steps

1. `t3` backend in `src/terminal.ts` behind `BackendName = 'herdr-app' | 't3' | 'test'`, selected by `T3CODE_THREAD_ID` + `T3CODE_CLI_PATH`; t3 runner tests with a fake runner (JSON fixtures from real `t3 thread show/list --json` output).
2. Lead registration and lock by thread id (`session.ts`, `digest.ts`); `/amigo` in a T3 thread runs `amigo brief` instead of refusing.
3. Dispatcher hook + `install-skill` writing it to user settings (prints the line, `--remove` takes it out); member and lead hooks route through it.
4. Watcher wake via `t3 thread send`; turn-end guard unchanged.
5. Interrupt/close playbook steps for the lead; README + `prompts/amigo.md` mention T3.

## Done when

- `amigo` (or `/amigo`) in a T3 thread prints the digest and holds the lock instead of refusing - checked by running it in a fresh T3 thread.
- A scratch survey runs end to end in T3: crew thread starts in a leased worktree, reports done, the watcher wakes the lead thread, `amigo close` cleans up - checked live in T3.
- `npm test` and `npm run typecheck` pass, including new t3 backend tests; existing herdr-app tests unchanged.
- A non-amigo Claude session pays only the dispatcher's no-op (no output, exit 0) - checked by timing the hook in an ordinary thread.

## Open questions

- Does `T3CODE_THREAD_ID` reach hook processes? (It reaches Bash; hooks are spawned by the same process, so likely, unverified.)
- Will T3 add CLI verbs for interrupt and archive? Until then two lifecycle actions depend on the lead calling MCP tools.
- Every Claude session on the machine runs the dispatcher hook (~100 ms node start per event). Acceptable, or gate it on `T3CODE_THREAD_ID` in a tiny shell check first.
